# Порядок разработки и проверки

Эти правила действуют для учебного проекта в этой папке.

1. До реализации каждой новой задачи выписать критерии из регламента и написать воспроизводимые тесты. Зафиксировать ожидаемый результат независимо от будущей реализации. Проверять обычный случай, границы допустимого диапазона, ошибочные входы и применимые отказы оборудования. Для исправления ошибки сначала воспроизвести её тестом.
2. Использовать документированные возможности установленной версии `pioneer_sdk2`, штатные библиотеки и проверенные примеры по «Пионеру Мини 2». Если в заимствуемом примере обнаружена ошибка, сначала показать её пользователю и обсудить изменение. Продолжать независимые задачи.
3. Реализовать задачу и прогнать тесты на локальном стенде. Для полётных команд подставлять имитацию SDK. Проверять последовательность команд, обработку устаревших или отсутствующих данных, прерывание маршрута и штатное завершение. При сбое проверить, какие команды фактически последовали.
4. После тестов отдельно прочитать логику целиком, от ввода до завершения. Сверить единицы, систему координат, критерии зачёта, работу с событиями и поведение при потерянной связи. Записать обнаруженные ограничения.
5. Проверить возможность запуска в совместимом полётном симуляторе. При успешном запуске записать название и версию симулятора, сценарий и наблюдавшийся результат. Если подходящая среда недоступна, отметить **«В симуляторе не проверено»**, указать причину и перейти к следующей задаче.
6. В отчёте указывать отдельно результаты стенда, проверки логики, симулятора и реального борта. Статус каждого этапа определяется фактическим запуском или проверкой.

Для существующего задания № 8 тесты добавлены после первой реализации. Воспроизвести стенд из корня проекта в PowerShell можно командой:

```powershell
& '.\.venv\Scripts\python.exe' -B -m unittest discover -s 'Тренировка' -p 'test_*.py' -v
```

## Проверка задания № 8 от 25 ноября 2026 года

- **Стенд.** Прошли 13 тестов. Один из них сверяет 300 маршрутов с независимым расчётом кратчайшей длины. Проверены ввод через терминал, порядок команд, отсутствие координат и события, отказ взлёта и неподтверждённая посадка.
- **Логика.** Лимит ожидания действует в цикле подтверждения точки. Отдельный блокирующий вызов SDK может пережить этот лимит. В частности, штатные `takeoff()` и `land()` в SDK 0.16.1 сами ждут события без тайм-аута. Запрос посадки по ошибке маршрута не гарантирует физическую посадку при обрыве связи.
- **В симуляторе не проверено.** Подходящий симулятор SDK 2 в проекте и среди зарегистрированных установок Windows не найден. Для «Геоскан Симулятора» производитель документирует подключение через SDK первого поколения. [Руководство производителя](https://docs.geoscan.ru/pioneer/soft/sim/geosim/)
- **На реальном борту не проверено.**

## Подсказка перед следующей правкой

Начать с [таблицы диагностики](Тренировка/Диагностика.md). Найти симптом, запустить указанный именованный тест, воспроизвести на том же PNG или CSV, затем прогнать все тесты. После проверки ограниченного ожидания событий 25 ноября 2026 года прошёл 71 тест. В полётных точках входа используйте confirmed_flight.connect. При обновлении SDK повторите ConfirmationTests, так как адаптер использует таблицу callback_events версии 0.16.1. Дополнительно прошли 375 прогонов посадочных зон, ворот и меток на дискретном поле с 75 вариантами расстановки. Для повторения доступны пять сценариев MuJoCo и четыре сцены виртуальной камеры. Результаты относятся к учебной модели. Вызовы взлёта и посадки SDK на реальном борту остаются непроверенными.

После добавления проверки профиля SDK прошли 73 теста. Перед разбором проблем камеры начните с sdk_profile.py и раздела «Профиль выданного борта» в диагностике.

Полный прогон выполняет Тренировка/check_home.py. Актуальные числа и статусы всех 11 заданий берите из автоматически обновляемого файла Тренировка/Результат домашней проверки.md. Для № 3–7 сквозные проверки камеры, динамики, контактов и посадки находятся в test_visual_mujoco.py.
